`SAD-383-fixtures/deals-card.real.html`. The faceout carries: image, `$251.99`,

### 2.3 Two structural facts discovered while capturing (not in the ticket)

1. **Every deals faceout is inside `.a-carousel-card`.** `parseAmazonCategoryPage`
   skips any candidate matching `el.closest('.a-carousel-card')`
   (`category-page.ts:301`). Measured: `deal faceouts=8, outsideCarousel=0`.
2. **`/b?node=` renders its product tiles inside carousels too.** Measured: 50 rating
   markers on the page, `[data-asin]` nodes = 0, and the 7 "cards" the parser resolves
   are hero banners (`title="New Beats 360 Headphones"`, `"Amazon Business Card"`).

Both are **card-discovery** defects, not rating defects. They are recorded in §12 of the
plan and deliberately **kept out of SAD-383's scope** — see the reason there.

## 3. The cheaper rating source, verified **[CAPTURE]**

The reviews popover endpoint answers with the same two values as the product page in
**3 KB instead of ~2.6 MB**:

```
GET https://www.amazon.com/gp/customer-reviews/widgets/average-customer-review/popover/?ie=UTF8&asin=<ASIN>
→ 200, 3,126 bytes
```

```html
<i data-hook="average-stars-rating-anywhere" … class="a-icon a-icon-star a-star-4-5"></i>
<h2 data-hook="acr-average-stars-rating-text" …>
  <span aria-hidden="true">4.6 out of 5</span>
  <span class="aok-offscreen">Average rating: 4.6 out of 5 stars</span>
</h2>
<span data-hook="total-review-count" …>142,457 global ratings</span>
```

| ASIN | popover rating / count | product page rating / count | agree? |
|---|---|---|---|
| B0BZYCJK89 | 4.6 / 142,457 | 4.6 / 142,457 | **yes** |
| B0CQVWT2NH | 4.6 / 21,842 | bestsellers card 4.6 / 21,842 | **yes** |
| B0CJZW65R3 | 4.7 / 206,997 | bestsellers card 4.7 / 206,997 | **yes** |
| B0DF472VMZ | 4.6 / 15,574 | bestsellers card 4.6 / 15,574 | **yes** |
| B0FB59FN5M | 4.1 / 15,647 | (deals card: none) | n/a |

**Negative control (must drive a guard):**

| ASIN | response |
|---|---|
| `B0ZZZZZZZZ` (valid shape, does not exist) | 200, `Average rating: 0.0 out of 5 stars`, `0 global ratings` |
| `B0ZZZZZZZ1`, `B0ZZZZZZZ2` | identical |

→ A non-existent ASIN still returns **HTTP 200 with a well-formed body**. The write must
therefore require `reviewCount >= 1 && rating > 0`; otherwise a collection could stamp a
fabricated `0.0` onto a row. Payloads are stored verbatim in
`SAD-383-fixtures/rating-popover.real.html` and `rating-popover.empty.real.html`.

The request needs no cookies (fetched logged-out, and `fetchPdpHtml` already uses
`credentials: 'omit'` for the same reason).

## 4. The parse cache freezes a card before its rating hydrates **[PROBE]**

`AmazonParseCache.isComplete()` (`parse-cache.ts:20-28`) treats a card as finished once
`asin + title + price + imageUrl` exist. `rating`/`reviewCount` are **not** part of that
test, so a card that prices and images before Amazon injects its reviews row is memoized
permanently for the life of that `Element`.

Executed probe (a search-layout card with the reviews row appended after the first pass):

```
pass1 (fresh cache)            rating=null
pass2 (same cache, row added)  rating=null   ← FROZEN
pass3 (fresh cache)            rating=4.5, reviewCount=1234
```

Why this only bites collection: the save path parses the card **once, on click**, with a
fresh DOM (and then enriches from the product page). The collection path re-parses the same
document every scroll pass — and is answered from the cache.

## 5. What the pipelines do with a missing rating **[CODE]**

| Fact | Evidence |
|---|---|
| Collection stores the card as-is; `addProducts` is fill-only and never invents a field | `db/products.ts:85-140` |
| Save continues into `enrichSavedProduct`, which lists `rating` and `reviewCount` in `DETAIL_FIELDS` | `background/enrich-saved-product.ts:36-37` |
| That stage is collection-visible only behind SAD-379's switch, **off by default** | `constants/defaults.ts:39`, `background/handler.ts:575-586` |
| When a row has no rating, enrichment fills it (fill-only merge, nulls never erase) | `enrich-saved-product.ts:mergeDetailIntoStored` (`FILL_ONLY_FIELDS` = price family only) |
| Drift detection threshold-checks only `price` and `imageUrl`; `rating`/`reviewCount` are tracked, printed, then ignored | `scraper/drift-telemetry.ts:137-160`, corroborated by `SAD-370` §3.3 (`rating:0, isDriftDetected:false`) |
| The card report cannot distinguish "layout has no rating node" from "node present but unparsable" | `scraper/card-diagnostics.ts:144-158` |
| Search-card rating coverage in the operator's own session was **0.96**; category-page cards **0/154** | `SAD-370` §3.2/§3.3 |

## 6. Conclusion this evidence supports

1. **Card-level rating extraction is not broken** on any layout that prints a rating:
   30/30 on a live bestsellers page, 0.96 on search per the operator's log.
2. **The deals/ProductCard grid carries no rating at all**, so no selector can fix it —
   the value only exists on the product page. That is the layout where a collection shows
   every other field and no rating, which is exactly SAD-383's description.
3. A save shows a rating on that same card because the **save pipeline fetches the product
   page**; collections only do so behind an off-by-default switch.
4. Two secondary defects make the symptom worse and hide it: the **parse-cache freeze**
   (§4) and **drift telemetry that cannot see rating nodes** (§5).

The plan in `SAD-383-rating-and-rating-count-plan.md` is built on exactly these four
statements, and §11 lists the experiments that would falsify each one.
